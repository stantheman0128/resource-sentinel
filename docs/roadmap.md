# Resource Sentinel roadmap

更新日期：2026-09-05

## 決策與範圍

本文件記錄本輪討論的方向，不代表新系統已建置或完成測試。目前只保存規劃；
不啟用常駐中控、不部署新的程序限制、不啟用雲端 adapter，也不送出雲端任務。
第二雲端是使用者重點期待的方向；先驗證一個 provider 的完整流程，再擴大。

既有實作架構見 [architecture.md](architecture.md)，接入方式見
[agent-integration.md](agent-integration.md)。本 roadmap 中的常駐服務是未來改版，
現有排程式採集與一次性 reconciliation 仍是當前架構。

## 已完成的局部監控調整

- 排除 Google Drive 虛擬磁碟的容量卡片、採集與新增容量事件。
- Commit 安全餘額由 12 GiB 改成 4 GiB，包含目前設定與程式預設值。
  已做兩個准入邊界測試；CPU、RAM、Commit 燈號與 I/O 條件仍獨立生效。
- 完整採集改成每分鐘 :00／:30 目標啟動，逾時跳過，排程 runner 避免重疊。
- 狀態發布以 5 秒倍數為目標；保留 sampled_at，generated_at 記錄實際發布時間。
  已觀察同一分鐘兩次採樣及一次對齊發布；尚非長時間效能或可靠性驗證。
- Dashboard 每 5 秒重新讀取快照。目前仍是頁面重載與約 30 秒資料採集，
  不代表每 5 秒量到新資料，也尚非工作管理員式的即時監控。

## 1. 約束能力分級：不能把模型自律當成強制控制

各產品、版本與執行模式的 hook／攔截能力必須逐一實測。Claude hook 是已有接入
路徑；不能推論其他 agent 永遠沒有 hooks，也不能推論有 hook 就涵蓋所有執行途徑。
模型、AGENTS.md、rules、提示詞與建議訊息都不是 OS 強制邊界。

| 等級 | 可做的事 | 必須揭露的限制 |
|---|---|---|
| 僅觀測／建議 | 量測、顯示規則、通知 agent | agent 可能忽略建議或直接啟動命令 |
| 合作式准入 | hook／wrapper／MCP 提交後取得 reservation | 只涵蓋有接入的命令入口 |
| 受管執行 | 中控 runner 啟動程序、追蹤整棵樹並套用 OS 控制 | 僅能保證受管工作，須驗證子程序逃逸及生命週期 |
| 遠端 adapter | submit/status/cancel/result 等已驗證操作 | 不能假設有 VM 管理權或可限制遠端 CPU/RAM |

每個 session 與 worker 都應顯示 control level、已驗證能力、覆蓋範圍、最近驗證時間，
並區分「已通知」「已准入」「OS 限制已確認生效」。自動發現的程序只算 inventory。

驗收重點：未經 wrapper 的命令、不同 shell、背景與脫離子程序、PID 重用、agent 重啟、
hook 失效、控制器崩潰。無法控制的工作必須標為 unmanaged 並計入外部負載。
禁止為取得全面控制而任意暫停或終止整個 IDE、桌面 UI 或無關程序。

## 2. 本地常駐中控：演算法優先，模型可選

- 小型常駐服務持有佇列與執行責任，SQLite 保留任務與資源帳本。
- session 提交一次任務後，中控等待容量、啟動工作並交付結果；不要求模型反覆讀紅燈。
- 支援 session 回呼／事件通知的 adapter 可送出明確執行許可；沒有此能力的介面，
  由受管 runner 直接執行命令，不能宣稱能任意喚醒或接管既有對話。
- 容量檢查、公平分配、等待時間加權與路由先使用確定性演算法，不依賴模型推論。
- 需要語意拆解時，由原 agent 或可選小模型提供結構化 task requirements；中控再驗證。
- 常駐服務需驗證空閒與負載下的自身 CPU/RAM/I/O 成本、單實例、崩潰恢復、
  事件去重、工作／reservation 生命週期，以及取消與重啟後的狀態一致性。

## 3. 公平而可調整的本機資源分配

- 對 session 的受管 build/test 工作分配 CPU 權重或配額；新工作加入時可重新分配，
  閒置份額可借用，避免先到者持續占滿。
- 評估 Windows Job Object：驗證受管程序樹、取消、CPU rate/weight 控制及既有 job
  相容性；不可把它描述為已部署功能。
- 優先級、等待時間加權、每 session 併行限制與短工作預算共同避免飢餓。
  允許小工作利用可用容量時，也要保障較大工作最終可執行。
- 保留使用者互動餘裕；避免將整個 IDE/UI 和 build 子程序一起降速。
- RAM 與 Commit 分別估算，利用歷史峰值、分位數與預估誤差校正，逐步替代粗略類別。
- 降低 CPU 或暫停程序不等於釋放 Commit。記憶體不足時使用降低工作併行、
  安全 checkpoint、可重啟階段 offload 或排隊；不以強制 trim 工作集充當容量釋放保證。

驗收：兩個及多個 session 的最小前進份額、短工作延遲、長工作飢餓、借用／回收份額、
記憶體預估低估、外部 unmanaged 負載突然增加及 UI 可操作性。

## 4. 統一入口與「第二雲端」

使用者以同一入口提交與追蹤工作。中控管理 Local 加上多個雲端 worker；
遠端對外呈現為一個資源池，內部仍按單一 worker、共享池與帳號配額分別核算。

路由條件：OS／工具／硬體、單次 CPU/RAM/Commit／磁碟需求、repo 與 base SHA、
path scopes、依賴、信任域／資料允許範圍、quota、併行數、probe 新鮮度、
啟動／傳輸／排隊成本與驗證位置。支援明確指定 Local 或 provider。

總容量只能作摘要；多台 worker 的 RAM 不會合成單一程序可用記憶體。
offload 必須移動實際命令執行，僅更換推論模型而仍在本機跑工具不算卸載。

交接單位為可重建工作：任務說明、必要上下文、不可變程式版本、明確納入的修改、
輸入 artifact 與驗證規則。已有 Windows 程序的 RAM、程序狀態、登入狀態不支援
通用的即時搬移；可使用安全 checkpoint 後在相容環境重啟。

Provider 優先評估已知有 CLI/API 入口者（如 Codex Cloud、Cursor Cloud）；
入口與帳號權限仍需部署時重新確認。其他 provider 逐一探索，不以 manual/bootstrap
記錄或可操作 UI 充當已完成自動化。自管 VM 可作為需要常駐服務與 OS 控制的另一類 worker。

每個 provider 的啟用門檻：

1. probe 與登入／授權／quota 檢查，保留證據與有效期限。
2. submit、狀態追蹤、取消、結果回收及錯誤分類。
3. base SHA 與輸入一致性、patch/artifact 完整性、指定驗證通過。
4. 網路失聯、submit 結果未知、控制器重啟、不重複派工、取消後資源釋放。
5. 真實小任務端到端通過後才啟用，記錄支援能力及不支援操作。

現有本機／狀態機測試不能替代各 provider 的真實端到端驗證。

## 5. 工作管理員式即時 Dashboard

目標是數字與圖表每 1 秒取得真正的新樣本，採增量更新，不重載整頁。
這是設計目標，不是已達成的效能承諾。

- 快路徑：使用持續開啟的效能計數器，量測整機 CPU、RAM、Commit、實體磁碟 I/O。
  避免每秒新啟動 PowerShell、掃完整 WMI 進程樹或查一次所有 provider。
- 慢路徑：約 30 秒更新完整進程歸因、GPU／環境 inventory 與摘要帳本；
  雲端 poll 依 provider 限制獨立設定，優先使用事件或 webhook。
- 顯示刷新與調度頻率分開：UI 可每秒；資源再分配初步每 5 秒加上任務事件，
  使用時間窗及 hysteresis 避免跟著每秒尖峰反覆調速。
- 本機 SSE／WebSocket 或輕量輪詢提供新樣本；服務限本機存取並驗證 Origin／授權，
  防止其他網頁呼叫管理操作。資料留在記憶體 ring buffer，持久化做批次／降採樣。
- 保留 sampled_at、published_at／received_at、樣本年齡與中斷標記；
  時鐘以整秒／5 秒刻度為目標，但不得偽造整齊時間或用動畫冒充新數據。
- RAM 與 Commit 分開標示；容量、進程寫入傳輸與實體 I/O 分開標示並寫明單位。

驗收：新資料端到端延遲、CPU/RAM/I/O 額外成本、頁面開關與多個觀察者、
斷線恢復、休眠／時鐘調整、資料缺口、Windows 計數器同時刻對照、
長時間穩定性。依量測決定 1 秒是否合適，必要時退至 2／5 秒。

## 建議里程碑（尚未開始設置與測試）

1. 接入與約束能力盤點；確認哪些工作能受管、哪些只能觀測。
2. 輕量即時遙測與 Dashboard，建立可信的資源與延遲量測基準。
3. 本機常駐中控、受管 runner、公平調度與故障恢復。
4. 一個雲端 provider 的真實端到端閉環，統一入口可追蹤與取消。
5. 擴大第二雲端資源池、自動選址及 Local／Cloud 聯合調度。
